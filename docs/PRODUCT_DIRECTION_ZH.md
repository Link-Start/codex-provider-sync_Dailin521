# 产品定位与演进方向

## 一句话定位

`codex-provider-sync` 的长期目标是让 Codex 会话能够 **本地优先地备份、跨设备带走，并在异常或切换后可靠恢复**。

它不负责登录、账号管理或 Provider 路由。CCSwitch 等工具可以负责切换供应商；本项目关注的是用户自己的会话数据如何安全留下、带到另一台设备，并在需要时恢复本地数据与历史可见性。

## 为什么这样定位

Provider 切换后的历史不可见是真实问题，也是当前项目已经验证的能力。但对更多普通用户来说，更长期、重复出现的需求是：

- 换电脑或重装系统后，希望保留已有会话；
- 在多台设备之间继续使用自己的 Codex 历史；
- 本地文件、索引或配置异常后，希望从可信备份恢复；
- 使用不同 Provider 工具后，希望旧会话仍能被 Codex 找到。

因此，Provider 同步应当保留为兼容性修复，而不是产品的全部边界。内部的路径、索引和 SQLite 对账仍然重要，但它们是保证备份与恢复可靠的工程基础，不应成为普通用户首页的主叙事。

## 当前已经提供

当前 `0.x` 版本已经提供：

- 发现当前 Codex Home、SQLite Home 和实际 `state_5.sqlite`；
- 检查 rollout、SQLite、项目路径和 Provider 元数据；
- 在写入前创建用于撤销本工具变更的托管恢复点，并支持保留、清理和恢复；
- 修复 Provider 切换后的历史会话可见性；
- 通过 CLI、本地 Web UI 和桌面 GUI 提供操作入口。

现有托管恢复点用于回滚本工具对元数据、配置和 SQLite 的修改，并不是完整聊天归档。当前版本**尚未**提供完整本地会话备份、可移植会话包、同步文件夹、自动跨设备同步或项目自建云服务。README 和界面必须把当前能力与路线图明确分开。

## 产品优先级

### 1. 完整本地备份与恢复

路线图第一步将提供普通用户最容易理解、也最可控的能力：看见最近备份、手动创建完整会话备份、验证完整性、预览恢复内容，并在恢复后再次检查结果。

### 2. 可移植会话包

导出适合跨设备传递的会话包，而不是复制整个 Codex Home。会话包至少应包含：

- 会话 rollout 与恢复所需附件；
- 格式版本、来源信息和内容清单；
- 每个文件的大小与哈希；
- 明确的导入计划和验证结果。

会话包不包含 `auth.json`、`config.toml`、Token 或账号凭据。它会包含聊天正文和附件，必须按敏感数据处理。导入器只有在目标 Codex 版本、schema 和字段来源已经通过夹具验证时，才可以重建或对齐索引；遇到未知布局时应停止并给出兼容性诊断，不进行猜测性写入。

### 3. 同步文件夹

第一阶段的跨设备同步采用用户选择的本地文件夹。用户可以把它放在 OneDrive、Dropbox、iCloud Drive、NAS 或其他已有同步工具中，本项目只负责生成、读取、验证和处理会话包。

写入时必须先使用暂存位置，最后写入完成标记；导入端只有在 manifest、逐文件哈希和完成状态全部验证通过后才接受会话包。外部同步目标可能读取其中的数据，因此在推荐云盘或远程 NAS 前，应先提供客户端加密，并清楚说明密钥丢失后的恢复边界。

这种方式比直接接入多个云账号更容易理解，也避免项目在早期承担账号授权、云端托管和持续运维责任。现有 `backups_state/provider-sync` 恢复点可能包含 `config.toml`，不得直接作为同步文件夹的数据源。

### 4. 可选同步适配器

在会话包和冲突模型稳定后，再考虑 WebDAV、S3 兼容存储等可选适配器。项目自建云服务不是当前或近期目标；若未来提供，也必须使用客户端加密，并让用户明确选择。

### 5. 兼容性修复

Provider、路径、索引和存储布局修复继续保留，但放在“修复”入口中。它们服务于历史恢复和异常处理，不要求普通用户先理解 rollout、SQLite 或 Provider ID。

## 跨设备数据模型

### 不同步正在使用的 SQLite 数据库

`state_5.sqlite` 以及它的 WAL / SHM 文件不是跨设备同步源。直接覆盖正在使用的数据库容易引入版本、锁、路径和事务状态冲突。

跨设备同步应以可移植会话包作为传输来源，而不是复制实时数据库。目标端只有在对应 Codex 版本和字段来源已经验证时，才能重建或对齐 SQLite；尚未证明能够从会话包无损恢复的字段必须保留兼容性门槛，不能把 SQLite 简化为必然可重建的纯派生状态。

### 冲突处理

会话按 thread ID 识别，并结合版本化的规范内容摘要判断是否相同。摘要规则需要排除 Provider、model 等允许修复的可变元数据，并通过兼容性测试固定下来：

- thread ID 与内容哈希都相同：跳过重复内容；
- thread ID 相同但内容不同：检测为冲突并停止或标记待处理，不静默覆盖；
- 目标端正在写入：推迟导入或标记为待处理；
- 导入完成后：重新验证文件、索引和可见性。

同一 thread 的事件级合并或分叉为新 thread ID，需要另行设计 rollout 路径、附件、SQLite 和全局状态的引用重写规则。在这些规则经过真实布局验证前，不承诺自动合并或“保留两个可继续版本”。

跨 Provider 或账号复制会话，并不代表目标后端一定能解密已有 `encrypted_content`。工具必须区分“数据已经恢复”和“会话能够继续推理”。

## 统一架构方向

CLI/Core 是唯一业务实现，负责发现、备份、校验、导入、恢复、同步与兼容性修复。界面只负责展示、确认、进度和平台交互。

目标结构：

```text
Browser host ─────────┐
                      ├─→ shared React presentation
Windows desktop host ─┘                │
                                       ▼
                           local versioned protocol
                                       │
                                       ▼
                                    CLI/Core
                                       │
                                       ▼
                      Codex local data + sync adapters
```

Windows 桌面包应内置运行 CLI/Core 所需的环境，让普通用户无需安装 Node.js。浏览器宿主可通过仅监听本机的服务调用协议，Windows 桌面壳可管理内置子进程；两者必须保持相同的能力语义，同时保留浏览器配对、防跨站请求和服务端路径授权。当前 Windows GUI 仍使用独立的 .NET Application/Core；迁移必须逐步进行，并在每一步保持已有的备份、锁、事务、回滚和路径安全行为。

机器协议与人类输出必须分离。桌面端和自动化使用版本化 JSON/JSONL 协议；终端文本可以独立优化。协议至少需要表达数据路径、能力版本、变更计划、进度、冲突、备份和最终验证结果。

## UI 方向

界面围绕普通用户的任务组织，而不是围绕内部存储表：

1. **首页：**同步状态、最近备份、最近设备与需要处理的问题；
2. **会话：**搜索、选择、导出和查看来源；
3. **备份与同步：**目标文件夹、进度、冲突和最近成功时间；
4. **恢复：**选择备份或会话包、预览影响、执行并验证；
5. **修复：**Provider、路径、索引和存储布局问题；
6. **活动与设置：**操作记录、保留策略和隐私选项。

首页不默认展示只有少数故障场景才需要理解的底层诊断项。出现问题时，再逐层展开证据和建议动作。

## 产品边界

- 不读取、修改、复制或管理 `auth.json`、账号凭据和登录状态；可移植会话包也不包含 `config.toml`；
- 不作为 Provider 市场、本地代理或账号切换器；
- 不通过修改 `updated_at` 强行改变会话排序；
- 不承诺恢复已经删除且没有任何备份的数据；
- 不承诺跨 Provider/account 解密或继续已有 `encrypted_content`；
- 不默认上传会话数据，任何外部同步目标都由用户明确选择；会话包包含聊天正文和附件，必须明确提示并支持客户端加密；
- 不把同步文件夹或云端文件当作无版本、无校验的覆盖源。

## 近期顺序

1. 保持 Provider 同步、备份和恢复的现有稳定性；
2. 定义统一的版本化 CLI/Core 机器协议；
3. 统一 React 界面，并将 Windows UI 逐步改为轻量桌面壳；
4. 设计并验证带 manifest、逐文件哈希、完成标记和客户端加密能力的可移植会话包；
5. 实现导出、预览导入、目标端索引重建和恢复后验证；
6. 在冲突模型稳定后加入用户选择的同步文件夹；
7. 最后再评估 WebDAV、S3 等可选适配器。

每一步都优先覆盖真实用户的常见路径。安全措施应服务于数据可恢复性，不为极端假设堆叠无穷确认。
