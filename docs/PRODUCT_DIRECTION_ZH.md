# 产品定位与演进方向

## 一句话定位

`codex-provider-sync` 是一个独立的 **Codex 本地会话数据诊断、修复、备份与迁移工具**。

它不负责登录、账号管理或 Provider 路由。CCSwitch 等工具可以负责切换供应商；本项目负责在任何切换方式之后，识别 Codex 实际使用的数据位置，解释会话为什么不可见，并以可备份、可验证、可恢复的方式处理本地会话数据。

## 为什么提升定位

Provider ID 不一致只是 Codex 本地会话问题的一种表现。真实会话状态同时分布在 rollout 文件、SQLite 线程索引、项目路径状态和不同 Codex Home / SQLite Home 中。用户看到的“历史消失”也可能来自路径失配、索引字段异常、存储布局变化或迁移不完整。

因此，Provider 同步应当作为一条修复规则，而不是产品的全部边界。

## 当前已经提供

- 发现当前 Codex Home、SQLite Home 和实际 `state_5.sqlite`。
- 诊断 rollout 与 SQLite 中的 Provider 分布、项目可见性、`cwd`、`has_user_event` 和锁定状态。
- 在备份后修复 Provider、model、SQLite 索引及 Desktop 项目路径元数据。
- 管理备份保留、恢复、事务回滚和跨 SQLite Home 恢复确认。
- 通过 CLI、本地 Web UI 和桌面 GUI 提供操作入口。

当前能力仍以“修复切换 Provider 后的历史会话可见性”为主要用户路径。

## 计划扩展的能力

- 诊断旧版与新版 Codex 存储布局之间的差异。
- 在明确来源和目标后迁移 Codex Home 或 SQLite Home。
- 生成可检查、可验证的会话备份包，并支持受控导入。
- 为设备迁移提供冲突检测、预览和恢复方案。
- 将诊断与修复规则做成 CLI/Core 的稳定能力，供不同界面复用。

这些是演进方向，不代表当前版本已经支持无条件的跨设备迁移。

## 架构原则

### CLI/Core 是唯一业务实现

状态发现、诊断、执行计划、修复、备份、恢复与迁移最终都应由 CLI/Core 提供。Web UI 和 Windows 客户端只负责展示、确认、进度和平台交互，不再各自复制数据处理逻辑。

目标结构：

```text
Windows UI ─┐
Web UI ─────┼─→ versioned CLI/Core contract ─→ Codex local storage
Automation ─┘
```

当前 Windows GUI 仍使用独立的 .NET Application/Core；迁移到统一 CLI/Core 应逐步进行，并在每一步保持现有行为和安全边界。

### 人类输出与机器协议分离

CLI 面向用户的文本可以持续优化；桌面端和自动化应使用版本化 JSON/JSONL 协议。机器协议至少需要表达：

- 已解析的数据路径和来源；
- 诊断项、严重度和建议动作；
- 写入前的变更计划；
- 进度、备份、跳过项和最终结果；
- 协议版本与能力协商。

### 先诊断、再计划、后执行

普通用户应当能够先看懂“数据在哪里、哪里不一致、会改什么”，再确认写入。安全措施服务于真实故障和可恢复性，不为极端假设堆叠无穷确认。

## 产品边界

- 不读取、修改或管理 `auth.json`、账号凭据和登录状态。
- 不作为 Provider 市场、本地代理或账号切换器。
- 不通过修改 `updated_at` 强行改变会话排序。
- 不承诺恢复已经删除且没有备份的数据。
- 不承诺跨 Provider/account 解密或继续已有 `encrypted_content`。
- 不默认上传会话数据；诊断、修复、备份与迁移以本地操作为基础。

“迁移成功”表示本地文件、索引和元数据按照计划完成复制或重建，不代表目标后端一定能够解密原供应商生成的推理内容。

## 近期顺序

1. 固化统一的状态与诊断模型，保持 CLI/Web 行为一致。
2. 定义版本化机器协议和变更计划格式。
3. 让 Windows UI 逐步成为 CLI/Core 的轻量客户端，并完善界面层级和反馈。
4. 将现有 Provider 同步整理为可独立诊断、预览和执行的修复规则。
5. 在真实 Codex 存储布局上实现并验证 Codex Home、SQLite Home 和备份包迁移。

每一步都应优先覆盖真实用户的常见路径，并通过临时夹具、自动化测试和必要的本机验证确认结果。
